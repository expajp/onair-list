# オンエア曲サイトの調査・運用メモ

2026-11-02 時点の記録。続きの調査を始めるときは、このファイルを読み込ませる。

- 公開ページ: https://expajp.github.io/onair-list/ （ANN0 は `#ann0`）
- リポジトリ: expajp/onair-list（public、`main` 直下を GitHub Pages で公開）
- Secrets: `X_BEARER_TOKEN`、`ANTHROPIC_API_KEY`。どちらもオーナーが GitHub に直接登録する。値は Claude に渡さず、チャットにも書かない。

## 共通の知見

### 使えるもの、使えないもの

- radiko（NoA API、アプリ）は両番組の時間帯のデータが空で使えない。
- X の読み方は2通り。
  - X API の recent search は直近7日のみで、自動更新が使う。1件約 $0.005。
  - Claude in Chrome は過去も読めるので、過去分の調査に使う。
- WebFetch では X を読めない（HTTP 402）。

### Claude in Chrome で X を調べるときの手順

- 検索語に `since_time:EPOCH until_time:EPOCH` を使うと分単位で絞れる。`since:YYYY-MM-DD until:YYYY-MM-DD` も使える。
- 次の方法で再読み込みなしに検索を切り替えると、`window.__*` の変数が残り、ページ内のループで連続検索できる。
  `history.pushState({}, '', url); dispatchEvent(new PopStateEvent('popstate', {state: {}}))`
- 連続検索するとレート制限で「やりなおす」が表示される。約16分待てば戻る。1件あたり20秒以上空ける。
- 裏タブでは `setTimeout` が約1分に1回へ間引かれる。`MessageChannel` で待つと間引かれない。
- ツールの出力は約1000字で切れる。結果を `window` に保存し、分割して回収する。
- `=&?%` を含む出力やURLは `[BLOCKED]` になるので、`.replace(/[=&?%]/g,' ')` で消す。
- 結果はタブの中にしかないので、回収するまでタブを閉じない。
- ブロッカー拡張が x.com を遮ることがある。回避せず、オーナーに解除を頼む。
- 投稿の絞り込みをキーワードで行うと曲名だけの投稿を落とす。時間帯で取り、本文を読むほうが確実。

### データの扱い

- 耳で確認した情報が最優先。情報源が「ポッドキャスト（耳で確認）」の行は、Xの結果で上書きしない。
- 一般語の曲名でヒットした投稿は、本文を読んで曲の話か確認する。例: 「やれんの」は曲ではなかった。
- 同じ回の行は必ず 野田→村上、もぐら→かたまりの順に並べる（ANN0 はオーナーの指定）。

### Apple Music のスクリプト

有料の Apple Developer 登録を避けるため、API ではなく Mac の Music アプリを AppleScript で操作する。

- `scripts/add_to_apple_music.applescript`: 番組、開始回、選曲者、プレイリストを指定して追加する。
  - `find_apple_music_tracks.py` が iTunes Search API で曲を探す（約20回/分、3.2秒間隔）。
  - カタログの曲を直接追加する命令がないため、再生→ライブラリへ複製→プレイリストへ複製→ライブラリから削除、の順で処理する。
- `scripts/sort_apple_music_playlist.applescript`: プレイリストを放送順に並べ替える。`sort_playlist_tracks.py` が順番を決める。
- 結果は `scripts/results/` に日時つきで残る（git 管理外）。

Music アプリの癖:

- `tell application "Music"` の中で `names` は予約語。
- 空のプレイリストに `name of tracks` を使うと -1728 エラーになる。
- `move` は位置がずれる。プレイリスト内で複製してから元の曲を消すと、ライブラリを変えずに並べ替えられる。

既知の未修正バグ: `find_apple_music_tracks.py` の出力で曲名の `"` が `\"` になる。曲名に `"` を含む曲は追加に失敗する可能性がある。

## 定期実行

`.github/workflows/update-onair.yml` が毎週火曜 12:00 JST に動く。手動実行で `check_episode` を指定すると、判定だけ確認できる。

1. RSS を取得し、未登録の回を探す。
2. X API で放送時間帯（火曜0:00から75分間）の @i_love_arata と @kuki_odoriba の投稿を検索する。
3. 選曲者を決める。

| 条件 | 選曲者 |
|---|---|
| 「1曲目」のみで、投稿が0:40より前 | 鈴木もぐら |
| 「1曲目」のみで、投稿が0:40以降 | 水川かたまり |
| 「サイコゥソング」 | 水川かたまり |
| 「2曲目」がある、またはリスナーの投稿 | リスナー |

4. 問題がなければ `main` に直接コミットする。次の場合は PR を作り、オーナーを担当者とレビュアーに指定する。
   - 2曲目がある
   - 公式と実況の曲が違う
   - 3曲以上ある
   - 検索できる7日を過ぎた
5. 曲の投稿が1件もない週は、曲なしの行を自動で追加する。

## 定期実行

`.github/workflows/update-ann0.yml` が毎週火曜 12:10 JST に動く。手動実行で `check_date` を指定すると、判定だけ確認できる。`--stats` で取得する時間帯を確認できる。

1. 直近の放送日（木曜）を求める。
2. `#マヂラブANN0 -is:retweet` を X API で検索する。取得量を減らすため、`ann0_song_times.csv` の統計から決めた時間帯だけを取る。
   - 既定の時間帯は 03:25〜03:50 と 04:15〜04:35。
   - 記録が5件以上たまると、直近20件の最小〜最大に前後5分を足した範囲へ切り替える。
3. 投稿が5件未満なら、放送なしとして何もしない。
4. Claude API（`claude-opus-5-5`）が投稿から曲を抽出する。見つけた曲の投稿時刻を `ann0_song_times.csv` に追記する。
5. `main` に直接コミットする。曲が分からない回は「曲の情報なし」の空行を追加する。
6. 次の場合は Issue を作り、オーナーへ通知する。
   - 曲が見つからない
   - 3時台の曲がない
   - 同じ時間帯に複数の曲がある
   - 抽出に自信がない
   - 前回の放送から1週間以上空いた

X の検索は直近7日までなので、金曜の放送を翌週火曜に取得する。Spotify を更新に使う案は、API の制限で不可と判明し採用しなかった。
